# ETL: Cloud Storage и Data Processing

## Часть 1. Перенос данных из PostgreSQL в Object Storage

Создан бакет `etl-postgresql-storage-kate`, который используется для хранения выгруженных данных и артефактов ETL-процесса.

![Созданный бакет etl-postgresql-storage-kate в Object Storage](image.png)

Для загрузки объектов в бакет создан сервисный аккаунт `storage-sa` с ролью `storage.uploader`.

![Создание сервисного аккаунта storage-sa с ролью storage.uploader](image-1.png)

В Managed Service for PostgreSQL развернут кластер `pg-etl-hw`; состояние `Alive` подтверждает его доступность.

![Доступный кластер PostgreSQL pg-etl-hw](image-2.png)

В базе данных создана таблица `x_tab`, в которую добавлены пять тестовых записей. Выполнение `SELECT` подтверждает исходное содержимое таблицы.

![Создание таблицы x_tab и исходные записи в PostgreSQL](image-3.png)

Для выгрузки данных настроен трансфер `postgresql-to-object-storage`: источником является PostgreSQL, а приемником - Object Storage. Статус `Завершен` подтверждает успешное выполнение первой загрузки.

![Завершенный трансфер из PostgreSQL в Object Storage](image-4.png)

В бакете появился CSV-файл, созданный в результате переноса данных из PostgreSQL.

![CSV-файл с выгруженными данными в Object Storage](image-5.png)

Для проверки повторной обработки исходные данные изменены: запись с `id = 41` удалена, а значение для `id = 42` обновлено на `Key3`.

![Изменение данных таблицы x_tab перед повторной выгрузкой](image-6.png)

После изменения данных трансфер запущен повторно; статус `Копируется` показывает выполнение загрузки обновленной версии данных.

![Повторный запуск трансфера после изменения данных](image-7.png)

Повторная выгрузка завершилась успешно, что подтверждается статусом `Завершен` и зеленой историей состояний трансфера.

![Успешное завершение повторной выгрузки данных](image-8.png)

На странице трансфера также видны настроенные эндпоинты PostgreSQL и Object Storage, использованные в ETL-процессе.

![Эндпоинты и успешный статус трансфера](image-9.png)

## Часть 2. Обработка данных с Apache Airflow и Data Processing

Для второй части задания выбрана упрощенная настройка инфраструктуры. Согласно руководству, при упрощенной настройке допускается использовать один сервисный аккаунт, один бакет с разными папками и не настраивать отдельные группы безопасности.

В качестве сервисного аккаунта используется `airflow-dataproc-sa`. В качестве бакета для DAG-файла, PySpark-скрипта, результата и логов используется `etl-postgresql-storage-kate`. Для разделения данных в бакете используются папки `dags`, `scripts`, `countries` и `spark-logs`.

В папку `scripts` загружен PySpark-скрипт, предназначенный для обработки данных в кластере Data Processing.

![PySpark-скрипт в папке scripts бакета](image-10.png)

Создан кластер Managed Service for Apache Airflow `airflow-etl-homework`; состояние `Alive` подтверждает, что среда готова к запуску DAG.

![Доступный кластер Managed Service for Apache Airflow](image-11.png)

В Object Storage загружен DAG-файл, который используется Airflow для оркестрации обработки данных.

![DAG-файл в бакете Object Storage](image-12.png)

Airflow обнаружил DAG `DATA_INGEST` с расписанием запуска `@hourly`.

![DAG DATA_INGEST в интерфейсе Airflow](image-13.png)

DAG активирован и запущен; в интерфейсе отображаются выполненные и текущий запуски процесса.

![Активированный DAG и история его запусков](image-14.png)

В логах задачи удаления кластера зафиксировано успешное завершение операции Data Processing после выполнения обработки.

![Логи задачи удаления временного кластера Data Processing](image-15.png)

Граф успешного запуска показывает последовательное выполнение трех задач: создание временного кластера, запуск PySpark-задания и удаление кластера.

![Успешный граф выполнения задач DAG DATA_INGEST](image-16.png)

Результат обработки записан в папку `countries` бакета: создан маркер `_SUCCESS` и CSV-файлы с выходными данными.

![Результирующие CSV-файлы и маркер SUCCESS в папке countries](image-17.png)
